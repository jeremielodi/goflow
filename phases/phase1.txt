Phase 1 — Core BPMN Runtime

This phase is the MOST important.

If Phase 1 is clean,
everything else becomes easier.

Supported BPMN Elements
Start Event
StartEvent → next node

Simple.

End Event

Marks:

execution complete
process finished if no more active executions
Sequence Flow
A → B

Just transition execution pointer.

Exclusive Gateway

This is your first real engine logic.

Example:

amount > 1000

You evaluate expressions and choose path.

Recommended:

use CEL
or Expr
or simple Go evaluator

Do NOT build your own expression language initially.

Service Tasks

This is critical.

Recommended architecture:

Workflow Engine
    ↓ creates job
Worker polls jobs
Worker executes logic
Worker completes job

Exactly like Camunda workers.

Example
{
  "type": "send-email",
  "variables": {
    "to": "john@test.com"
  }
}

Worker:

worker.Subscribe("send-email", handler)
User Tasks

Store in DB.

Users:

claim
complete
reassign

This becomes your Tasklist equivalent.

BPMN Parsing

You should internally convert BPMN XML into:

type Node struct {
    ID   string
    Type string
    Next []string
}

And:

type ProcessGraph struct {
    Nodes map[string]*Node
}

VERY important:
Build graph once during deployment.

Do NOT parse XML during execution.

REST API

POST /processes/{key}/start

Body:

{
  "variables": {
    "amount": 1200
  }
}
Get Tasks
GET /tasks
Complete Task
POST /tasks/{id}/complete

MOST IMPORTANT DESIGN DECISIONS
1. Separate Runtime from BPMN

BPMN is ONLY:

a definition
a graph

Runtime is independent.

This is VERY important.

2. Execution Token Model

Your engine should work like token movement.

Example:

Start
 ↓
Task A
 ↓
Gateway

Execution pointer moves node to node.

This is the heart of BPMN engines.

3. Async-first architecture

Never block execution thread.

Everything:

jobs
timers
notifications
workers

Should be async.

4. Idempotency

VERY important.

Workers may retry.

Never assume single execution.

Final Advice

Your biggest risk is NOT technical.

It is:

overengineering too early
trying to support all BPMN elements
adding clustering too soon

Keep it:

simple
deterministic
observable
async

A focused BPMN engine in Go for enterprise workflows is absolutely realistic.
