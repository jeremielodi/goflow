# Switching from Camunda 7 / Camunda 8

What an application already running against Camunda needs to change to run against GoFlow. "Tested" means covered by the integration suites with that client; anything else is expected to work from the API shape but hasn't been verified with that client.

## Camunda 8 (Zeebe gRPC, `/v2` REST)

| Area | Status | What to do |
|---|---|---|
| Zeebe gRPC clients | ✅ tested with **zeebe-node 8.3** (all 19 RPCs), **zeebe-client-java 8.3.22** and **camunda-client-java 8.8.44** (core commands and job workers, see [Java client](java-client.md)) | Point the gateway address to `goflow-host:26500`. With `camunda-client-java`, set `.preferRestOverGrpc(false)`: its REST mode can't parse GoFlow's `/v2` responses. Spring Zeebe and `@camunda8/sdk` haven't been tested; `MigrateProcessInstance` and `UpdateJobTimeout` (newer clients) don't exist yet. |
| Authentication (gRPC) | ✅ | Same credentials as REST, in the `authorization` metadata: `Bearer` with a GoFlow JWT (`POST /auth/login`) or an OIDC token, or `Basic` with a GoFlow e-mail and password (zeebe-node's `basicAuth` and camunda-client-java 8.8's basic-auth provider, both tested; zeebe-client-java 8.3 has no basic-auth provider, so give it a `CredentialsProvider` that sets the header, see [Java client](java-client.md#zeebe-client-java-83)). A call without valid credentials gets `UNAUTHENTICATED`. A client configured with OAuth against Camunda Identity won't authenticate unless GoFlow's OIDC points at the same provider. `GRPC_ALLOW_ANONYMOUS=true` brings back calls without credentials (they run as the first super_admin) for trusted local networks. The gateway has no TLS. |
| `/v2` REST | ✅ subset (list below) | Same paths and request shapes. **Keys are UUID strings**, not 64-bit integers, and the responses are simplified: a client typing keys as numbers breaks — camunda-client-java in its REST mode fails with `MalformedResponseException` — while one treating them as strings works. |
| User tasks | ⚠️ | GoFlow user tasks are **not jobs**: a worker on the job type `io.camunda.zeebe:userTask` (job-based user tasks, Tasklist's mode before Camunda 8.5) receives nothing. There is no Tasklist API either. Find and complete user tasks over REST: `POST /v2/user-tasks/search`, `/v2/user-tasks/:key/assignment`, `/completion` (or the Camunda 7 `/engine-rest/task` API). |
| Keys across gRPC and REST | ⚠️ | gRPC hands out 64-bit keys, REST uses UUIDs, and no endpoint converts one into the other. An application that starts an instance over gRPC and then needs it over REST (its user tasks, say) has to find it by a business variable; starting it over REST, with a `businessKey`, avoids that. See [Java client](java-client.md#what-the-grpc-side-cant-do). |
| BPMN models | ✅ | Run as they are: `zeebe:` task definitions, I/O mappings, FEEL, called elements, multi-instance, message subscriptions, timers, signals, escalations, compensation, user tasks with forms. |
| Operate, Tasklist, Optimize, Connectors, Web Modeler | ❌ | Not provided. GoFlow has its own frontend (instance inspection, task inbox, analytics, in-browser modeler). The Desktop Modeler can deploy through the gRPC gateway; choose its basic authentication with a GoFlow e-mail and password (not tested since the gateway started requiring credentials). |

`/v2` endpoints available: `POST /v2/process-instances`, `GET /v2/process-instances/:key`, `POST /v2/process-instances/search`, `POST /v2/process-instances/:key/modification`, `POST /v2/jobs/activation`, `POST /v2/jobs/:key/completion`, `/failure`, `/error`, `POST /v2/user-tasks/search`, `POST /v2/user-tasks/:key/completion`, `/assignment`, `DELETE /v2/user-tasks/:key/assignee`, `POST /v2/messages/publication`, `POST /v2/signals/broadcast`, `POST /v2/incidents/search`, `POST /v2/incidents/:key/resolution`, `POST /v2/flownode-instances/search`, `POST /v2/variables/search`, `POST /v2/decisions/:key/evaluation`, `GET /v2/forms/:formKey`, `POST /v2/resources/deployments`, `GET /v2/topology`.

## Camunda 7 (`/engine-rest`)

| Area | Status | What to do |
|---|---|---|
| Authentication | ✅ | HTTP Basic (GoFlow user e-mail and password) or a GoFlow JWT. |
| External task workers | ✅ | `fetchAndLock` (with `asyncResponseTimeout` long polling, the topic's `variables`, Camunda's `LockedExternalTaskDto` fields), `complete`, `failure` (`retries` = what remains, 0 raises an incident), `bpmnError`, `extendLock`, `unlock`. Tested with the Java **camunda-external-task-client 7.24.0** (fetch-and-lock, complete, failure with retry, Basic and JWT auth; it needs `jaxb-runtime` on the classpath, see [Java client](java-client.md#2-camunda-7-external-task-client)). Its Spring Boot starter hasn't been tested. Not provided: `GET /external-task` queries, `setRetries` on an external task (use `POST /engine-rest/job/{id}/retries`), priorities. |
| Starting instances | ✅ | `POST /engine-rest/process-definition/key/{key}/start` (and `.../tenant-id/{tenantId}/start`, `/{id}/start`, `submit-form`) with typed variables and a `businessKey`; Camunda's `ProcessInstanceWithVariablesDto` in return. `GET /engine-rest/process-definition/key/{key}`. Business keys are stored (migration `006`) and can be searched: `GET /engine-rest/process-instance?businessKey=`, `GET /engine-rest/history/process-instance?businessKey=`. |
| User tasks | ✅ | `/engine-rest/task/...` as in Camunda 7: query (GET and POST), count, get, claim, unclaim, assignee, complete, submit-form, form key, variables — see [API Reference](api.md#camunda-7-task-api-engine-resttask). Not provided: delegation, candidate users/groups management, comments, attachments, identity links. |
| Deployment | ✅ | `POST /engine-rest/deployment/create`, multipart, with `deployment-name` (and optionally `tenant-id`). |
| Process instances, variables, incidents, history, messages, signals | ✅ | `/engine-rest/process-instance/...` (variables, suspension, deletion), `/engine-rest/variable-instance` (query, count), `/engine-rest/incident`, `POST /engine-rest/job/{id}/retries`, `/engine-rest/history/process-instance` (GET and POST, Camunda 7 states `ACTIVE`, `COMPLETED`, `EXTERNALLY_TERMINATED`…), `/history/activity-instance`, `/history/task`, `POST /engine-rest/message`, `POST /engine-rest/signal`. `POST /engine-rest/message` works as in Camunda 7: typed or plain `correlationKeys` and `processVariables`, `businessKey` and `processInstanceId` targeting, `all`, `204` or the result list with `resultEnabled`, `400 MismatchingMessageCorrelationException` when nothing waits; not `localCorrelationKeys` nor message start events (use `/v2/messages/publication`). Incidents lack some `IncidentDto` fields (`causeIncidentId`, `rootCauseIncidentId`, `configuration`, `processDefinitionId`), which the REST client Spring Boot starter requires. |
| Java clients | ✅ | Tested, see [Java client](java-client.md): the External Task Client 7.24.0, the OpenAPI REST client (`camunda-engine-rest-client-openapi-java` 7.24.0), and the REST client Spring Boot starter 7.24.1, which runs an application written against `RuntimeService`, `TaskService`, `RepositoryService`, `ExternalTaskService` and `HistoryService` against GoFlow. |
| BPMN models | ⚠️ must be adapted | **No Java**: `camunda:class`, `camunda:delegateExpression`, JUEL `camunda:expression` and Java listeners can't run. Turn Java service tasks into external tasks (`camunda:type="external"` with `camunda:topic`, or a `zeebe:taskDefinition` type) handled by a worker, and conditions into FEEL. Camunda 8 models need no change, so moving a Camunda 7 model to GoFlow is close to the Camunda 7 → 8 migration. |
| Cockpit, Tasklist, Admin webapps | ❌ | Not provided; see the GoFlow frontend. |
